Створи статичну демо-сторінку, яка візуалізує розподіл пацієнтів між провайдерами за навантаженням (load factor) і показує, чому з'являється перекіс, коли додається новий провайдер або змінюються робочі години.

## Алгоритм
Це новий порожній репозиторій. Відтвори в JS такий алгоритм:
- Для кожного провайдера **load factor = кількість призначених пацієнтів / робочі години на тиждень**.
- Провайдери з 0 годин у виборі не беруть участі.
- Наступного пацієнта отримує провайдер із **найменшим load factor**. При рівності береться перший у списку.
- Після призначення лічильник пацієнтів цього провайдера збільшується на 1.

Проблема, яку треба продемонструвати: новий провайдер починає з 0 пацієнтів, тобто його load factor дорівнює 0. Він завжди найменший, тому ВСІ нові пацієнти йдуть до нього, доки його load factor не наздожене решту. Те саме станеться, якщо в існуючого провайдера збільшилися години: його load factor різко впав.

## Вимоги до результату
- Один файл `index.html` у корені репозиторію (HTML + CSS + чистий JS inline, без збірки, без бекенду, без npm). **Жодних бібліотек і фреймворків** (ні з CDN, ні локально): лише чистий HTML, CSS і JavaScript. Графіки роби власними силами на SVG/CSS, без зовнішніх шрифтів, іконок та скриптів.
- **Мова інтерфейсу: англійська.** Усі підписи, кнопки, підказки й тексти на сторінці англійською.
- **Мобільна версія обов'язкова:** адаптивна верстка (mobile-first), без горизонтального скролу, зручні тап-зони (≥44px), таблиця на вузьких екранах перетворюється на картки.
- **Favicon:** inline SVG favicon через `<link rel="icon" href="data:image/svg+xml,...">` (проста іконка, наприклад стилізовані терези або три стовпчики).
- Підтримка світлої й темної теми через `prefers-color-scheme`.
- Правильний `<title>` і `<meta name="viewport">`.
- Сторінка має працювати на GitHub Pages: усі шляхи відносні.
- **Justfile** у корені з рецептами:
  - `serve` (за замовчуванням): запускає локальний сервер статики на `http://localhost:8000` і виводить цю адресу. Сервер працює всередині Docker, наприклад `docker run --rm -p {{port}}:8000 -v "$PWD":/site:ro -w /site python:3.12-alpine python -m http.server 8000`. Порт бери з параметра: `serve port="8000":`.
  - `open`: відкриває сторінку в браузері (`xdg-open`). Це єдиний рецепт, що працює на хості.
- **Усе виконується в Docker.** Якщо знадобиться збірка (хоча за замовчуванням її немає), а також будь-які інші скрипти, лінтери чи тести, запускай їх лише всередині Docker-контейнера через рецепти justfile. На хості не мають бути потрібні ні Node, ні Python, ні інші інструменти, окрім `just` і `docker`. Фіксуй версії образів (наприклад `python:3.12-alpine`, не `latest`).
- Використовуй лише загальну термінологію (provider, patient, hours per week, load factor). Не додавай назв компаній, продуктів чи внутрішніх систем ні в код, ні в текст, ні в README.

## Рушій (JS)
Реалізуй за описом вище:
- `pickProvider(providers)`: відфільтруй `hours > 0`, візьми провайдера з мінімальним `loadFactor` (при рівності перший у списку).
- `assign(provider)`: `patientCount++`.
- Рушій чистий, без залежності від DOM, щоб його було легко тестувати.

## Блок пояснення "About this demo" (згортний)
У верхній частині сторінки, одразу під заголовком, має бути блок, що згортається й розгортається. Реалізуй через нативні `<details>/<summary>` зі стилізацією (без JS-залежності), з анімованою стрілкою. Він згорнутий за замовчуванням, але розгорнутий при першому відвідуванні (стан не зберігай). Заголовок: "About this demo: the problem and the fix".

Текст англійською, коротко й простими словами, у чотирьох підрозділах з малими підзаголовками:
1. **How distribution works.** Кожен новий пацієнт іде до провайдера з найменшим load factor (patients ÷ weekly hours). Провайдер із більшою кількістю годин природно отримує більше пацієнтів.
2. **The problem.** Новий провайдер починає з 0 пацієнтів, тобто з load factor 0, і поки він не наздожене інших, кожен новий пацієнт іде тільки до нього. Те саме відбувається, коли в існуючого провайдера збільшуються години: його load factor різко падає. Результат: "burst" на одного провайдера замість рівномірного розподілу.
3. **What this demo shows.** Історія подій (було → стало), як змінюється load factor після додавання провайдера чи зміни годин і куди йдуть наступні пацієнти.
4. **Possible fixes.** Три стратегії з режиму Compare (Fair start, Batch cap, Smooth weighted round-robin), по одному реченню на кожну, з підказкою, що їх можна переключити нижче й порівняти результат.

Додай міні-ілюстрацію на SVG/CSS: два горизонтальні бари "Before / After new provider", де видно, що весь потік пацієнтів іде до нового провайдера. Блок має добре виглядати на мобільних екранах і в обох темах.

## Інтерфейс
1. **Providers table/cards.** Колонки: name, hours/week (редагуються inline), patients, load factor (3 знаки), share of total patients (%), горизонтальний бар. Провайдер із мінімальним load factor підсвічений як "next candidate". Кнопка видалення провайдера.
2. **Add provider.** Кнопка "Add provider" відкриває форму: name (за замовчуванням наступне ім'я зі списку нижче) і hours/week (слайдер 1–60 + числове поле). Новий провайдер з'являється з `patientCount = 0`.
3. **Edit hours.** Зміна годин існуючого провайдера записується в історію як окрема подія.
4. **Add patients.** Поле N із швидкими кнопками 10 / 50 / 100 / 500 і кнопка "Distribute". Розподіл відбувається покроково з легкою анімацією (можна пропустити кнопкою "Skip animation"). Видно, хто отримує кожного нового пацієнта.
5. **Distribution chart.** Стовпчики кількості пацієнтів по провайдерах і маркер load factor. Після розподілу відображай "before → after" для кожного провайдера.
6. **History timeline (ключова фіча).** Журнал подій; кожна подія зберігає знімок стану:
   - Initial state (seed)
   - Provider added (name, hours)
   - Hours changed (old → new)
   - Patients distributed (N, і скільки отримав кожен провайдер)
   Кожен запис показує дельту по провайдерах (було → стало, load factor до і після) і короткий висновок, наприклад: "Emily received 100 of 100 patients (100%)". Клік по запису показує стан на той момент (read-only перегляд з кнопкою "Back to current"). Спільна шкала на графіку допомагає побачити стрибок.
7. **Skew indicator.** Показник перекосу, наприклад: частка найбільшого отримувача в останній пачці й різниця між max/min load factor. Якщо один провайдер отримав >60% пачки, показуй попередження "Skew detected".
8. **Scenarios (preset buttons):**
   - "New provider joins": seed → додати провайдера на 40 год → розподілити 100.
   - "Hours increased": seed → збільшити години в одного з 20 до 40 → розподілити 100.
   - "Reset": початковий стан.
9. **Початковий стан (seed):** 4 провайдери з історичними даними, наприклад 40h/400, 30h/300, 20h/200, 10h/100 (усі з load factor 10), щоб спочатку все було рівномірно.

## Бонус: порівняння з виправленням (режим "Compare")
Перемикач "Current logic / Fixed logic" або вид side-by-side на тих самих вхідних даних:
- **A. Fair start:** новому провайдеру при додаванні ставиться `patientCount = round(hours × середній load factor інших)`.
- **B. Batch cap:** не більше K підряд до одного провайдера.
- **C. Smooth weighted round-robin:** розподіл пропорційний годинам.
Стратегію вибирай випадаючим списком. За замовчуванням "Current". Біля кожної стратегії короткий опис однією-двома фразами. Логіка "Current" має точно відповідати алгоритму вище.
